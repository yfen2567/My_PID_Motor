# v2.3.1 M1 IDLE 时序基线报告

## 1. 测试结论

**PASS（采用 10 μs 周期抖动容差）**

本次在电机停止、UART 目标源、`target=600` 条件下采集 20 个时序样本，确认 ControlTask 的空闲基线稳定，且通信链路没有产生队列或 TX 错误。

本次 PASS 不是简单地把第一次结果改成通过，而是经过了“发现异常—定位范围—提出原因—调整判定口径—重新验证”的过程。原始日志全部保留，未被覆盖。

## 3. 测试过程中发现的问题

### 3.1 第一次 M1：严格 10 ms 阈值下出现累计超期

第一次 M1 原始日志为：

```text
logs/v2.3_m1_timing_idle_baseline_raw_20260906_140949.txt
```

当时使用严格判定 `period_us > 10000U`。日志中：

- `exec_us` 稳定为 `20`；
- `tick_exec_us` 稳定为 `14`；
- `period_us` 大部分为 `9999～10000`，但出现 `10001`、`10002` 和 `10010`；
- `timeout_count` 从 `7` 增长到 `13`。

这里首先要区分两件事：`timeout_count` 是 `StartControlTask()` 启动以来的累计值，不是发送 `timing stats` 后才开始计数。因此测试开始时已经是非零，并不代表本次 M1 一开始就产生了这么多超期。

### 3.2 第二次 M1：重复现象，且控制体执行时间仍稳定

第二次 M1 原始日志为：

```text
logs/v2.3_m1_timing_idle_baseline_raw_20260906_141304.txt
```

这次仍然看到：

- `exec_us=20`；
- `tick_exec_us=14`；
- `period_us` 大部分接近 `10000`，偶尔达到 `10001`、`10002`；
- `timeout_count` 从 `16` 增长到 `23`。

### 3.3 根据字段关系定位问题范围

`exec_us` 表示从本轮 ControlTask 起点到本轮任务主体结束的时间，`tick_exec_us` 表示 `Control_Tick10ms()` 的执行时间。两者在上述两次测试中都基本稳定，但 `period_us` 偶尔超过 10000 μs。

因此，现象不像是 `Control_Tick10ms()` 内部计算变慢，也不像是 ControlTask 主体本身持续变长；更合理的怀疑是：任务执行完进入阻塞态后，到下一次真正恢复运行之间出现了额外延迟。也就是说，问题范围应优先放在 FreeRTOS 的 tick 唤醒、调度和中断抢占路径，而不是直接归因于控制算法。

## 4. 原因分析

`vTaskDelayUntil()` 保证的是基于 FreeRTOS tick 的周期唤醒，不保证以 DWT 测量的微秒级绝对精确。当前系统中，以下因素都可能造成少量调度抖动：

1. SysTick 本身只能按 tick 分辨率参与调度；
2. 更高优先级的 USART1 中断可能延迟 ControlTask 恢复执行；
3. UART 中断发送是逐字节进行的，发送期间会持续产生中断活动；
4. DMA 或其他 HAL 外设中断可能短暂抢占任务恢复路径；
5. 临界区会暂时关闭中断，使 tick 处理或任务切换延后；
6. 任务从阻塞态转为就绪态后，还要等待调度器实际恢复该任务运行；
7. `SystemCoreClock` 到微秒的整数换算、DWT 读数和整除也会引入少量测量误差。

当前证据支持“微秒级调度/唤醒抖动”的解释，但不能仅凭串口日志证明具体是哪一个中断或临界区造成了某一次延迟。要进一步分辨，需要 GPIO 波形、逻辑分析仪、示波器或更细粒度的 RTOS trace；这属于 M4 及后续诊断范围。

## 5. 判定口径调整

将严格的：

```c
if (period_us > 10000U)
```

调整为当前阶段的容差判定：

```c
if (period_us > 10010U)
```

含义是：允许 10 ms 周期存在不超过 10 μs 的微小调度抖动，只有超过 `10010 μs` 才累计 `timeout_count`。这不是删除或掩盖原始测量值：`period_us` 仍然原样输出，后续仍可从日志中分析 `9999～10002` 的细微波动。

如果未来需要更严格地研究这类抖动，应增加 `sample_count`、最小/最大周期、最大绝对抖动等原始统计，并把“原始周期超出 10 ms”和“超过可接受 deadline 容差”拆成不同计数，而不是继续修改唯一阈值来解释所有现象。

## 6. 调整阈值后的实测结果

20 个 `TIMING_STATS` 样本中：

- `period_us` 范围：`9999～10000`；
- `exec_us`：稳定为 `20`；
- `tick_exec_us`：稳定为 `14`；
- `timeout_count`：从 `0` 保持到 `0`，未增长；
- 电机状态始终为 IDLE，PWM 为 0，fault 为 NONE。

代表性样本：

```text
TIMING_STATS period_us:10000,exec_us:20,tick_exec_us:14,timeout_count:0
TIMING_STATS period_us:9999,exec_us:20,tick_exec_us:14,timeout_count:0
TIMING_STATS period_us:10000,exec_us:20,tick_exec_us:14,timeout_count:0
```

最终 `comm stats`：

```text
rx_overflow:0
line_q_full:0
cmd_q_full:0
pool_fail:0
tx_drop:0
tx_error:0
rx_restart_fail:0
```

## 7. 判定

- IDLE 软件状态稳定：通过；
- ControlTask 周期接近 10 ms：通过；
- 控制任务执行时间和 `Control_Tick10ms()` 时间稳定：通过；
- 按 `period_us > 10010U` 判定无超期：通过；
- UART、命令队列、对象池和 TX 链路无错误：通过。

## 8. 范围边界

本报告验证的是当前固件在 IDLE 和正常串口通信负载下的软件时序基线。它不证明电机运行、命令压力或 GPIO 物理波形行为；M2、M3 和 M4 分别覆盖这些后续范围，其中 M4 需要逻辑分析仪或示波器。
